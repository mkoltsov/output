What “all messages” can honestly mean

All messages currently accessible to your authorized account, across the selected topics and time range. No API can promise recovery of deleted, expired, hidden or inaccessible content, every past edit revision, or all missed deletion events.

The group advertises visible history, which is encouraging. That flag does not prove the human account’s membership or actual retrieval access. A future implementation must test that account’s view against the official client.

Default member invite permissions appear enabled, but account-specific restrictions, join approval and bot admission remain unverified. Metadata is evidence of policy, not permission to add the bot automatically.

Choose the smallest access model that meets the requirement.

Bot API can be enough for future supported group traffic. If group policy permits adding the existing privacy-disabled bot, admin promotion is not inherently required for ordinary group messages. Add the target as a separate configured source, retain the existing source, explicitly request the required update types and keep one polling consumer.

This does not backfill group history, guarantee every message type or reconstruct deleted content. Current bot-to-bot settings can expand delivery; older FAQ claims about all other-bot messages are too absolute. Check current feature behaviour rather than promising completeness.

Recommended for the stated history requirement: a separate MTProto user-session reader. Register your own Telegram application, authorize your account once using the normal code/2FA or QR flow, and verify ordinary account access. Use Telethon for a focused Python adaptation; consider TDLib if building a larger maintained client.

The bot remains useful for a separate authenticated owner interface. A bot token inside Telethon remains a bot; changing libraries does not enable user-only history and topic-list methods. A user session carries broad account authority, so protect it as carefully as a password and isolate its process.

A user client can read only what that account is allowed to see. If the user already has legitimate group access, a normal user-session reader does not depend on bot admission. If access is denied, the application must report that boundary and stop rather than try alternate identities or mirrors.

Guest Mode provides only summoned mention/reply context; it does not provide history or a continuing stream. It is disabled on the inspected bot anyway. Public web previews, business-recipient APIs and the profile-chat history method are not substitutes for forum history.

Terms and privacy shape the design

Telegram’s published terms restrict scraping beyond ordinary legitimate use and restrict uses involving AI deployment. The stated exception depends on individual, informed and continued consent in the relevant context. No such consent was established for third-party group members.

The default design is therefore a legitimate personal-client feature with proportionate local state and deterministic alerts. Do not feed the group into Codex, AI summarization, public transcripts or a permanent content archive by default. Local storage alone does not establish compliance with every proposed use.

This is an implementation boundary based on the published terms, not a legal opinion. Reading a group as a member does not automatically authorize downstream AI use of everyone’s content.

1. Split the current responsibilities before adding a source

The existing fetch_updates() is a Bot API ingestion function. Keep it for the separate owner interface. Introduce MtprotoForumReader behind a small SourceReader interface. The new forum reader must never call handle_private_message(), queue_forum_mentions(), process_forum_mentions() or any Codex/file/command dispatcher.

Replace the single chat constant with a private source registry. Store a source key, username, resolved numeric peer identity, enabled flag, all-topics scope, history policy and notification policy. Pin the resolved peer so a username change cannot silently redirect collection. Default allow_reply=false and allow_ai=false. Preserve the current source as a distinct entry.

2. Normalize events without flattening edits, topics or identity

Replace the current message-only shape with MonitorEvent: source key, peer type/ID, message ID, event kind, sent/edited UTC timestamps, topic root, immediate reply parent, minimal sender peer, text/caption, typed media metadata, grouped-media ID and historical flag.

Key messages by (source_key, peer_id, message_id). MTProto has no Bot API update ID; do not pretend a message ID is one. Upsert edits without incrementing new-message counts. Use version/digest-based notification keys. Keep service and media-only events explicit. Map General and unresolved topics deliberately; an immediate reply ID is not necessarily a topic root. Avoid downloading media unless a separate feature requires it.

3. Replace JSON checkpoints with a transactional inbox/outbox

A complete received batch and the application cursor must become durable together. Store source cursors, minimal current-message state, bounded pending events and notification delivery state in private SQLite. Keep live update recovery separate from history pagination. Advance delivery state after successful delivery, not in a general finally block.

Use one database writer, a restrictive umask, a private directory and limited retention. A deleted/expired message should lose its stored body; retain only the minimum tombstone needed for reconciliation. Never let old history pages overwrite newer edits or resurrect a known deletion. Back up live SQLite with database-aware semantics.

4. Close the live/backfill race and report incomplete recovery

Connect only an already authorized session; a background job should report authorization required rather than launch an interactive login. Register new/edit/delete handlers first, stage their events durably, capture a history boundary, then traverse history to that boundary. Replay queued live events through the same version-aware upsert path and reconcile an overlap window.

Let the library preserve MTProto sequence state and perform difference recovery. An application message high-water mark is insufficient for older edits and deletions. Library session persistence and application database commits are separate durability boundaries; use overlap reconciliation and a visible coverage-gap state. Deleted messages that were never observed and expired protocol differences cannot be reconstructed reliably.

5. Keep notification and error handling outside the ingestion loop

Run bounded notification workers from the outbox. Historical messages should not generate a flood of alerts by default. Respect FloodWait deadlines and Bot API retry hints; use capped backoff with jitter for transient failures. Treat revoked sessions, target mismatch and lost access as actionable blocked states. Do not repeatedly retry an entitlement or authorization denial.

Prefer counts and deep links over sender names or full text in push notifications. Use an authenticated private transport. Preserve ambiguous-send state for reconciliation. Keep ingestion responsive while delivery or owner commands are slow. Do not create a new permanent service as part of this research; agree the deployment lifecycle separately.

6. Instrument the new MTProto boundary and prove the user-visible result

Set OTEL_SERVICE_NAME=telegram-reader. Existing HTTP monkey-patching does not instrument the MTProto socket transport. Add explicit RPC/job boundaries, sample every third successful call, always record failures and export atomic low-cardinality metrics to the existing textfile pipeline. Surface failures and stale sources in the automation snapshot and digest.

Track authorization/connection separately from last source sync, topic-inventory age, backfill position, unresolved gaps, oldest pending alert, queue size and last successful notification. Do not label telemetry with message text, usernames, phone numbers, account IDs or session data. A connected socket must not be presented as proven complete coverage.

AccessStatus must separately report authorized, target_matches, member, forum, history_accessible, history_lower_bound, live_connected and coverage_unknown. A successful socket or metadata request cannot collapse these into one healthy flag.

PROTOCOL DETAILS

The details a basic listener would miss.

The client interfaces were inspected without installation or authorization. These details belong in the acceptance checklist.

Whole-dialog history and exact topic cursors

The official Desktop exporter uses a whole-dialog history pass as a baseline. A topic-scoped export separately includes the topic root and traverses replies. Use topic traversal to validate/repair coverage rather than repeatedly downloading the whole forum through every path.

Current Telethon 1.45.0 contains functions.messages.GetForumTopicsRequest(peer, offset_date, offset_id, offset_topic, limit, q=None). Begin with zero IDs and no date. Carry all three cursor fields between pages. Respect order_by_create_date: use the final topic’s creation date when ordered that way, otherwise the date of its final message where known. The message ID and topic ID are separate offsets.

For message history, persist the oldest returned message ID as an exclusive backward cursor; keep a fixed upper boundary and use the iterator’s documented offsets. For a topic, page replies with the topic root kept separately. Stop only on documented exhaustion, not merely a short page. Detect repeated/non-advancing IDs, deduplicate overlap, checkpoint each accepted page and report a failed page as partial retrieval. A restart resumes the persisted scope and cursor.

Deduplicate pinned/reordered topics, reject a non-advancing cursor, persist progress and recheck the head after the pass. Approximate topic counts are progress hints, not a completeness certificate.

The wheel was downloaded in memory and its SHA-256 matched PyPI metadata. This verifies package integrity relative to that metadata, not a separate publisher signature.

Topic identity, service messages and peer IDs

Received messages use reply_to_top_id, not the send-request field top_msg_id. Preserve the immediate reply separately. The normalizer for this known forum should follow:

topic creation service → its own message ID
forum_topic = true     → top ID, else reply ID
ordinary forum post    → General (1)
malformed topic data   → unknown + reconcile

The convenient Telethon NewMessage event omits MessageService. Supplement it with deduplicated raw channel-update handling or use a consistent raw event adapter. Do not filter acquisition by sender, keywords, media or incoming-only flags when the requirement is all accessible content.

Keep peer type with its ID. Bot API marked chat IDs, Telethon event IDs and an entity’s positive raw ID are not interchangeable. Convert with library utilities; never copy access hashes between accounts.

Recovery and memory bounds

sequential_updates=True serializes handlers but uses an unbounded internal queue. It does not cap workload. Keep handlers fast, commit immediately and bound queued bytes and worker concurrency. If ingestion overflows, record a coverage gap and reconcile; never silently discard.

A live high-water message ID cannot recover edits/deletes of older IDs. Preserve library difference state and perform bounded cache reconciliation. Deletion events are not perfectly reliable. Remote delivery is at least once unless the destination provides a working idempotency mechanism.

05 / EXECUTION ORDER

A sequence that preserves working features.

These are recommended implementation phases. They have not been applied to the computer.

PHASE 01

Contain and make truth visible

  • Constrain the chat responder and reduce credential scope.
  • Review current package metadata and enable an effective maintenance policy.
  • Represent blocked/failing/overdue outcomes explicitly.
  • Repair chronic source and publication failures with isolated fixtures.
  • Bound router recovery actions before a future outage.

Exit condition: no known false-green product status; private state cannot enter a public commit; external chat cannot reach host actions.

PHASE 02

Make recovery dependable

  • Introduce shared inbox/outbox and outcome helpers where they solve proven defects.
  • Preserve session identity on retries; keep unknown presence distinct.
  • Complete connector pagination and shared-state locking.
  • Harden telemetry errors and verify critical transport spans.
  • Encrypt backups and complete an isolated restore/coverage drill.

Exit condition: crash and timeout fixtures produce the right durable state; restore time and remaining gaps are documented.

PHASE 03

Add the scoped forum reader

  • Choose future-only bot visibility or account-visible history.
  • Authorize and probe the user session only for the chosen route.
  • Validate topics, versions, recovery and deterministic alerts.
  • Then measure storage churn and simplify supervision.

Exit condition: the agreed scope matches official-client observations; gaps are visible; no arbitrary group input gains execution capability.

OPERATIONAL FOLLOW-UPS

Small changes with practical value.

Printing: credentials and completion delivery

The server responds while the physical printer is offline. A synthetic completion-notifier failure was acknowledged and not retried on the next poll. Reuse a durable delivery state rather than marking notification success from process completion alone. Inventory clients that use the global OctoPrint key and migrate to separate revocable application keys before a server upgrade removes that compatibility.

OctoPrint application keys ↗

Graceful optional-workload shutdown

Preserve the existing user-selected idle policy, including its exact definition of downloading. The current stop mechanism forcibly removes containers. Prefer a bounded graceful application shutdown followed by VPN teardown, using forced removal only as a deliberate fallback. No current resume-state corruption was observed, and the stack was absent during the audit.

Make telemetry-launch failure a deliberate policy

The shared launcher requires collector startup before running the business command. If collector startup fails, unrelated products can be suppressed. Define per-product behaviour: durable local telemetry and an explicit launch failure, bounded deferral where appropriate, and safe handling for critical device actions. A monitoring outage must not silently become an unrelated automation outage.

Keep a real power and boot recovery exercise

UPS readings, configured shutdown directives and clean power flags are useful evidence. Estimated runtime does not prove battery autonomy, shutdown correctness or recovery boot. Plan an attended, scoped exercise after recovery coverage is in place. Keep retained storage-migration evidence until a separate retention decision; do not delete it as routine cleanup.

For every implementation: preserve current configuration and state; test in isolation; apply one scoped change; verify useful outcomes locally and in telemetry; retain a rollback path. No new persistent scheduler is needed to deliver this audit.
06 / METHOD AND LIMITS

Evidence you can distinguish.

Three specialist agents, independent Codex process reviews, primary documentation and isolated reproductions were integrated and cross-checked.

LIVE

Current local and remote state

Host resources, processes, services, timers, mounts, listener responses, remote telemetry and narrow Telegram metadata. Successful polling of the existing source is not target coverage.

RECORDED

Logs and receipts

Recent wrapper outcomes, retained failure streaks, backup upload verification and source freshness. These establish recorded events, not every external delivery.

SOURCE

Code and configuration

Launch routes, retry branches, publication manifests, action reachability and update policy. Code presence is distinguished from recent invocation.

REPRODUCED

18 isolated defect probes

AST-extracted production functions with synthetic data and stubbed effects. No production imports, chat sends, device controls or live-state writes.

INDEPENDENT

Separate Codex review

Separate read-only Codex CLI reviews examined sanitized source and the final report in isolated workspaces. Conclusions were checked against live evidence and synthetic fixtures.

UNVERIFIED

Explicit acceptance work

Full account-visible forum coverage, internet exposure, complete disaster recovery and every external product result. Lack of evidence is not a success claim.

What the audit did not do

No production code, package policy, credential, firewall, bot membership, workflow or schedule was changed. No scheduled email/device job was invoked. No Telegram user login, message send, history export or second Bot API poller was started. Optional print/model sessions were not disturbed.

Read-only checks, a private isolated package-index refresh, cloud metadata reads and private synthetic fixtures were used. Representative restore files and temporary OAuth copies were removed after validation; production credentials stayed unchanged. The report itself is the only intended public output; detailed source evidence and raw state are not published.

Coverage without overclaiming

The local scheduling inventory is substantial, but “all automation” has no reliable universal discovery mechanism. Remote hosts, SaaS schedules, dynamically spawned scripts and dormant tools can escape a local inventory.

Local scans found no additional configured Codex automation directory or desktop autostart directory. One repository workflow was present on disk; its cloud enablement/run history remains unverified. A scan found 47 direct local skill entries and 37 Python skill scripts, with 25 lexical network candidates. Only one had explicit local instrumentation markers; inherited launch wrappers mean that is not a coverage percentage. Build an actual critical-path registry before drawing that conclusion.
