Investigation date: 16 November 2026 · Sanitized technical plan

Measure ComfyUI runs with OpenTelemetry

Start with an external observer of the existing jobs API. Send one trace per run through the existing Alloy gateway. Add detailed node observation as a separately verified second phase.

Plan only — instrumentation has not been deployed

Publication boundary. This page contains the implementation plan and sanitized findings. It excludes credentials, tenant identifiers, private endpoints, machine addresses, user paths, run identifiers, prompts, workflow contents and generated media.

What the investigation established

  • Active collector: Grafana Alloy runs as a user service. Readiness and component-health endpoints returned success. Its OTLP trace pipeline is receiver → memory limiter → resource detection → batch → authenticated OTLP HTTP export to Grafana Cloud.
  • Active transport: accepted and exported span counters increased during observation. The trace exporter queue was empty in both samples; no collector warning/error journal entries appeared in the inspected 30-minute window. Historical failed-send counters exist, so this does not prove lossless delivery.
  • Network boundary: OTLP receivers listen only on loopback. A sender on another machine needs a deliberate transport path.
  • Existing metrics: a separate Prometheus pipeline scrapes a textfile collector every 120 seconds. An existing automation failure summary is consumed by the automation snapshot/Morning Digest code.
  • Existing benchmark artifacts: a one-shot LTX benchmark helper and saved metrics are present on the execution host. These establish prior benchmark instrumentation, not general monitoring of ordinary ComfyUI runs.
  • Available run data: the installed jobs API returned acceptance, execution-start and terminal timestamps, outcome, workflow ID and output count for recent completed jobs. The observed history also contains timestamped lifecycle and cache events.
  • Not verified: no new diagnostic span was submitted and retrieved from Grafana. No general ComfyUI telemetry service was deployed. Output existence or an application success event does not establish visual quality.

Recommended first phase

ComfyUI jobs/history API ↓ loopback read-only polling External observer on execution host ↓ bounded local spool + authenticated SSH tunnel Alloy gateway on collector host ↓ existing authenticated export Grafana Cloud traces Observer aggregates → atomic textfile relay → existing metrics scrape Sanitized run failures → existing automation summary → Morning Digest

Run the observer in its own environment and user service. Keep ComfyUI's Python dependencies and execution process unchanged. Use OTEL_SERVICE_NAME=comfyui-observer, explicit source host identity and the observed ComfyUI revision. Cloud credentials remain on the collector host.

Use the existing bootstrap/wrapper patterns where appropriate, but give the observer its own lifecycle: a cron process span is not a workflow run span. Instrument observer HTTP/network calls every third logical call and always record their failures. Exclude the telemetry exporter from recursive instrumentation, and surface export/tunnel failures through dedicated observer-health signals.

Trace structure

  • comfyui.run: accepted timestamp → terminal timestamp.
  • comfyui.queue: accepted timestamp → execution-start timestamp.
  • comfyui.execute: execution-start timestamp → terminal timestamp.

Reconstruct timestamps from the server's millisecond timestamps, converting correctly to the SDK's nanosecond units. Polling adds discovery delay, not polling-sized uncertainty to these stored durations. Detect missing or inconsistent timestamps; do not fabricate precise intervals. Run totals exclude request validation before acceptance and may exclude final post-execution bookkeeping.

Allowlisted trace attributes: opaque run/workflow identifiers, configured workflow family, execution host, ComfyUI revision, outcome, output count, cached-node count when available, and sanitized error/node types. Keep raw prompt graphs, node inputs, preview paths, media, exception messages and tracebacks out of export by default. Optional benchmark parameters require an explicit safe-field mapping.

Acquisition and recovery

Poll bounded pages from /api/jobs, with an overlapping reconciliation window and pagination until the checkpoint is reached. Inspect per-run history only when needed. Do not repeatedly fetch complete queues or histories containing large workflows. Keep a durable local ledger keyed by execution-instance identity and run ID, deterministic trace/span IDs, and bounded retention.

Persist newly observed terminal runs before export, replay after outages, and distinguish discovered, queued-for-export and acknowledged records. Stable IDs help control replay, but do not claim exactly-once backend ingestion across an acknowledgement loss. History is held in process memory with a finite cap, so a sufficiently long outage or restart can permanently remove evidence.

A disappearing queued item, lost server connection or missing terminal event is an unknown/incomplete observation unless corroborated. Record known user interruption separately from execution failure. A server-reported success is application success; validation of generated media remains a separate concern.

Gateway change required before cross-host traces

The current resource-detection stage detects the collector machine. Its installed Alloy version defaults to override=true. This creates a source-identity hazard for remote spans. Prefer a dedicated receiver/route for remote observer data that retains the memory limiter and batching while bypassing collector-host resource detection. Merely preserving supplied fields can still fill missing fields with gateway identity.

Back up the affected gateway configuration, validate a candidate configuration, then apply the smallest route change. Preserve existing local automation pipelines. Keep receivers bound to loopback and use an SSH tunnel for the pilot. Verify source identity in the retrieved trace. Alloy's installed-version resource detector source confirms the override default.

Metrics and operational diagnosis

Record every observed run in counters and duration histograms, independently of HTTP span sampling. Initially export all run-level traces, since each run needs only a few spans. Sample routine observer API calls every third call, retaining all failures. Reduce successful trace detail only after measuring volume; head sampling cannot later recover a trace that develops an error.

  • Run counts by bounded workflow family and outcome; separate failed, interrupted and unknown observations.
  • Queue, execution and total duration histograms; compare like-for-like workflow revisions and cache conditions.
  • Queue depth, age of oldest queued run, current run age, server reachability and observer heartbeat.
  • Export backlog, oldest unexported record, dropped records, tunnel availability and last successful gateway contact.
  • Later, execution-host CPU/RAM and GPU memory/utilization/temperature sampled on a bounded cadence, correlated by source host and time. This is correlation, not proof that resource pressure caused a failure.

Write aggregates atomically to the existing textfile directory on the collector host. A file written only on the execution host is not scraped by the remote collector. Relay monotonic counters/histogram buckets without resetting them at each poll, and publish freshness metrics. Do not place run IDs, trace IDs, prompt text or arbitrary errors in metric labels. The current 120-second scrape cadence suits aggregate dashboards; use observer state for prompt stale-run detection.

Relay each sanitized failed run once into the established failure-summary format, with kind=automation-job and a trace ID. Keep observer transport errors separate from failed workflow runs, and avoid counting one run failure again for each failed HTTP poll. Extend the existing automation snapshot/Morning Digest renderer; do not add another notification scheduler. Emit stale/unavailable status when the observer or relay stops.

Second phase: trustworthy node spans

A generic independent WebSocket connection cannot reliably see jobs submitted by another client: lifecycle and node events are addressed to the submitting client ID. Reusing that ID replaces the browser's socket mapping. Normal history also lacks general per-node timing, and the executed event is not emitted for every node.

Add a narrowly scoped local event bridge only if node attribution is needed. Keep export outside core ComfyUI. Verify its lifecycle integration against the installed revision: progress-handler registration is replaced per run, and lazy evaluation, asynchronous nodes and expanded subgraphs make “the next node starts when the previous one ends” an invalid general timing rule.

Capture explicit timestamped starts, finishes and failures with run/node identity and cache/attempt/subgraph information. Name spans for stable node classes. Treat application timing as distinct from CUDA kernel timing; avoid per-node GPU synchronization that would distort performance. Submission validation errors require caller/proxy or explicit submission hooks because rejected requests never enter jobs/history.

Implementation order and acceptance criteria

  1. Offline observer: exercise recorded synthetic job data for success, failure, interruption, cache reuse, missing timestamps, pagination, restart and replay. Verify sanitization and bounded labels.
  2. Gateway and transport: back up and validate the separate remote route, establish the tunnel, submit a small diagnostic trace, and retrieve it by trace ID. Check source host, timestamps, parenting and exporter health.
  3. Read-only pilot: observe existing jobs without altering the queue; compare exported durations and outcomes against the exact jobs API records. Mark pre-pilot history separately to avoid confusing backfill with new runs.
  4. Metrics and digest: verify the remote textfile is scraped, fresh data reaches Grafana, and a synthetic sanitized failure appears in a renderer-only snapshot preview. Verify that notifications are not accidentally sent during the preview.
  5. Controlled failure and outage tests: after the queue drains, use an isolated minimal test to prove failure attribution. Simulate observer/tunnel interruption without disturbing ComfyUI; verify bounded buffering, replay, freshness and duplicate control.
  6. Node pilot: only after both running and pending queues are empty, load the bridge in an isolated or scheduled test. Verify cached, asynchronous and expanded-node cases before broad use.

Measure pilot overhead and actual daily trace volume before setting a budget. As a planning formula, three spans per run means roughly 3 × observed runs run-level spans, plus sampled transport diagnostics. Node spans add the number of observed node attempts. These are estimates, not measured cloud intake.

Rollback: stop the independent observer and tunnel, preserve its ledger, and restore only the backed-up gateway route if needed. No change to active workflows is required for phase one.
