The selected rule

Cache text + captions→Observe multiple removals→Copy to the pinned chat

Two distinct cached texts removed from one topic qualify, even when their updates arrive in separate batches. A lone removal, a pair from different topics, expired content and unknown message bodies do not qualify. Copies include the original timestamp and topic identifier.

Telegram does not identify who deleted a message or supply a dependable deletion timestamp. Every copy says “Removal actor unknown.” The 60-second window uses observed update times; it is a bulk-removal heuristic, not proof of an administrator action.

What was verified

Capture → edit → delete → copy. Synthetic end-to-end messages using real pinned Telethon request and update types.
Replay and crashes. Atomic message/cursor commits; acknowledged copies do not repeat. Uncertain sends remain ambiguous.
Access and scope. User authorization, numeric peer pins, membership failures, finite pagination and visible gaps.
Expiry and protection. Stale, unknown, protected and expiring content cannot become a removal copy.
Delivery boundaries. Same-topic threshold, window limits, destination matching, FloodWait and Unicode chunking.
Observability. Every third logical API call plus every failure; private health, atomic metrics and existing Digest integration.

No real forum messages were collected or reposted during implementation. The local readiness check reports setup required, with zero Telegram API calls.

Complete the private setup

The pilot and its isolated environment are installed in ~/dev/telegram-reader-pilot. Run the following locally. Application credentials and login codes are entered through hidden terminal prompts; they must stay out of chat and public files.

cd ~/dev/telegram-reader-pilot
./pilot doctor
./pilot authorize
./pilot pin
./pilot run --watch-seconds 300
./pilot run --watch-seconds 300 --send

Register your own Telegram application using API development tools. The account must legitimately access both chats and be able to send text in the destination. The pin step resolves the requested destination from account-visible dialogs and verifies the source forum. It sends nothing.

The first run captures and queues without sending. The --send run automatically delivers qualifying copies for that invocation. Configuration starts disabled; each run is an explicit finite foreground command. No service, timer or persistent scheduler was installed.

Practical limits of this pilot

  • The bootstrap reads at most 500 messages and 20 topic pages. A cap or failed page is partial coverage, not a complete forum archive. Compare General and several other topics with the official client during acceptance.
  • Live handlers precede backfill; cached versions and deletion tombstones share one transactional writer. Live event caps and disconnected periods are exposed as gaps. Telegram deletion updates are not perfectly reliable.
  • Text deleted before it was cached is unavailable. Media files are not downloaded. Protected and self-destructing content is excluded. A source metadata change conservatively clears the cache and stops copying until access is verified in a new invocation.
  • Sending commits durable state before the request. Unknown outcomes are held as ambiguous and are not automatically retried. This prevents automatic duplicate attempts but may require local reconciliation.
  • Expiry is checked before every copy. The running process purges expired cache content. If the pilot is stopped, physical cleanup of content expiring while stopped waits until the next invocation. Already delivered destination posts follow that chat’s retention policy.
  • The default watch lasts 300 seconds, with a maximum of 3600 seconds. Continuous monitoring requires a separately requested deployment and a live acceptance run.
