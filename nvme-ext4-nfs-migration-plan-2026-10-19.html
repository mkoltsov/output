NVMe NTFS to ext4 migration and NFSv4 transition runbook

Prepared: 19 October 2026. Revision 2: consolidate all NVMe partitions into one ext4 volume. Storage layout rechecked for this revision; service and backup observations retain their earlier inspection time on the same date.
Status: plan only. No copy, checksum pass, mount change, format, package installation, service interruption, or NFS configuration was performed while preparing this document.

1. Outcome and fixed decisions

Replace the NVMe's entire four-partition layout with a new GPT containing one ext4 data partition, restore the useful main-volume files at their existing local paths, verify them, and then migrate approved Linux network clients to NFSv4.

  • Remove all four existing NVMe partitions and create one GPT Linux data partition spanning the usable disk, formatted ext4. The new data device will be partition 1 (currently this would be /dev/sda1); there will be no separate EFI, reserved, or Windows recovery partition.
  • Keep /mnt/disk1_part1 and its main-data directory layout, now backed by the new partition 1. Retire /mnt/disk1_part2 and all of its live configuration dependencies. Old EFI/recovery contents are retained only as temporary off-device images for recovery, not recreated or merged into the live data tree.
  • Use an off-NVMe file copy on the microSD as the default staging destination; keep it outside the home directory and outside routine home backups. A second copy on a separate device is preferable if available.
  • Use ext4 defaults with a 1% reserved-block allocation, plus nodev,nosuid. Games may need execution, so do not mount the whole volume noexec.
  • Restore local storage first. Retain SMB only for a controlled compatibility window, then switch clients to NFS in a separate phase.
  • Use an NFSv4-only server, explicit approved client addresses, selected child exports, and a dedicated anonymous share identity. Private backups and the existing private exchange tree are excluded.
  • Do not add a migration scheduler. Existing monitoring must cover the changed mount and new sharing service.

Destructive boundary: the first old-filesystem signature erasure begins whole-NVMe destruction, before GPT creation or ext4 formatting. Execution authorization must cover the exact physical NVMe, removal of every old partition, verified off-device copies, impact, and recovery approach. The user's requested scope is incorporated here; this update changes the plan only.

Complete these before setting a maintenance window:

  3. Inventory all local and remote consumers, including scripts containing either old UUID or mount path. Confirm client owners, mount paths, approved addresses, and their read/write needs. Idle TCP connections do not constitute a complete client inventory.
  4. Validate the staging filesystem identity and free space. Require projected staging size, small-partition images, logs, and at least 30 GB additional free root space. Recalculate if data has grown. Check inode availability as well.
  5. Determine whether any Windows ACLs, alternate streams, encryption, reparse objects, or other NTFS-only metadata must survive. Linux file copies preserve only metadata exposed by the mount. If any irreplaceable NTFS-specific information is needed, add a raw image on a separate device before any signature erasure or repartitioning.
  6. Decide the exact broken-entry exception. Recover or specifically waive it. Do not broaden the exception to hidden files, Windows metadata folders, or all unreadable entries.
  7. Verify that all required tools are present: rsync, GNU find/sort/xargs/sha256sum, sfdisk, parted, partprobe, udevadm, wipefs, blkid, mkfs.ext4, e2fsck, ACL/xattr tools, and the tools for each archive format being preserved. Stop conditions: unexpected device identity; insufficient staging space; missing administrative recovery access; unapproved private-data exposure; any unexplained copy/read/hash error; any active writer that cannot be quiesced; unverified staging data; or any NVMe partition that remains mounted or held when destructive work would begin.

4. Phase A — preserve configuration and make the initial copy

  1. Save lsblk and mount inventories; dump the GPT with sfdisk --dump "$NVME_DISK". Save checksums of the saved evidence.
  2. Copy, with original ownership/mode/ACLs, /etc/fstab, Samba configuration and drop-ins, the mount guard, backup program and units, health exporter, storage findings, relevant consumer configuration, and client mount configuration. Record enabled/active states separately.
  3. Capture old partition 4 from its stable read-only recovery filesystem, plus images of unused old EFI partition 1 and reserved partition 2. Use dd if=... of=... bs=4M status=progress conv=fsync with exact stable partition selectors and no conv=noerror. Any read error stops the image step. Hash and verify the images before any signature erasure. These small off-device images preserve a recovery option without retaining their partitions on the rebuilt NVMe.
  4. These small images plus the partition table do not contain the main data filesystem and are not a full-drive rollback image. Do not attempt an uncompressed 256 GB full-drive image in approximately 193 GB of free space or assume compression will make it fit.
  5. Run an initial whole-tree copy, including dotfiles and hidden system directories. The source trailing slash matters; never use "$NVME_MOUNT"/*.

Initial copy template, before adding any specifically approved exception:

rsync -aHAXSx --numeric-ids --info=progress2 \
  "$NVME_MOUNT/" "$MIGRATION_WORK/data/" \
  >"$MIGRATION_WORK/logs/initial-copy.log" 2>&1

The known bad entry is expected to prevent a completely successful unfiltered copy. After recording and explicitly waiving it, add exactly --exclude=/.codex-smb-onboot-write-test to every main-tree copy and comparison, and prune precisely that path from source inventories. A successful repeat must exit zero. Do not accept rsync status 23 merely because one known entry exists.

Review any ACL/xattr errors independently: NTFS ownership and modes are synthesized by mount options, and some Windows metadata cannot be transplanted to ext4. If preservation flags fail, identify each attribute, document what Linux exposes, retain a metadata inventory, and stop until its treatment is agreed. Do not silently remove -A or -X or suppress errors.

The initial copy can run while normal writers remain active. It is a warm copy and cannot authorize signature erasure, repartitioning, or formatting.

5. Phase B — freeze writers and prove the staging copy

  1. Record current states again. Stop the home-backup timer first, then allow any backup service to finish normally. Do not kill an archive/upload mid-write.
  2. Notify known clients of the outage through the agreed channel. Inspect root smbstatus, stop Samba, and prevent automatic restart or new sharing sessions for the maintenance window.
  3. Stop only actual NVMe consumers. Gracefully close Kodi/RetroArch and stop torrent containers if running. Do not stop unrelated Docker, containerd, or OctoPrint simply because they are active.
  4. Check root-level open files and working directories with fuser -vm or lsof, running copies, hashes, backup jobs, and all mount namespaces used by containers. An unprivileged empty listing is insufficient.
  5. Remount the main NTFS filesystem read-only and confirm ro. If it is busy, find and resolve the holder; do not force or lazily unmount.
  6. Reconcile the frozen source into the dedicated staging tree. A deletion pass may target only this migration's data directory, after reviewing a dry run and confirming its filesystem identity and path. Never apply deletion to the source.
  7. Produce the final source manifest and path/type inventory while the source remains read-only. If the known exception is approved, use exactly the same exclusion throughout.

rsync -aHAXSxnic --delete --numeric-ids \

Independent content and tree verification

Build a deterministic manifest containing relative filename, size, and SHA-256 for every regular file; inventory directories, symlink targets, special file types, and hardlink relationships separately. Handle names with spaces, newlines, and non-UTF-8 bytes without loss. A one-shot Python implementation should use byte paths with Base64 encoding in its private manifest, lstat, O_NOFOLLOW for regular-file opens, and explicit errors; reject unknown special types until reviewed.

The following GNU checksum pattern is a simpler content-check template. GNU escaped checksum records handle unusual filenames; do not combine --zero output with sha256sum --check.

(
  cd "$NVME_MOUNT"
  find . -xdev -type f -print0 |
    LC_ALL=C sort -z |
    xargs -0 -r sha256sum --
) >"$MIGRATION_WORK/manifests/source.sha256"
(
  cd "$MIGRATION_WORK/data"
  sha256sum --check --strict "$MIGRATION_WORK/manifests/source.sha256"
) >"$MIGRATION_WORK/logs/staging-sha256-check.log" 2>&1

If the one-entry waiver is approved, the find expression must prune ./.codex-smb-onboot-write-test before evaluating file type. Without this, traversal may fail even though rsync excludes it.

Also run a zero-change rsync dry run using the frozen source and stage. Checksums alone do not detect extra files, missing empty directories, or incorrect symlinks. Retain file counts and total sizes as supplementary evidence, not substitutes for hashes.

Test every backup archive with its format-specific integrity tool, then spot-restore representative home and Fedora files into a private scratch directory. Document any archives not tested; an unexplained archive failure blocks all destructive work even if the migration copy matches the corrupt source.

Whole-drive destruction gate: source frozen; zero unexplained read errors; final copy exits zero; staging checksums match; tree comparison has zero unexplained differences; archive checks pass; old GPT and all three small-partition images are verified off-device; all exceptions are signed off; source manifest and configuration backup are retained outside the NVMe. This gate precedes the FIRST signature wipe, not just mkfs.

Remove old signatures and create one partition

The following is the destructive execution template. Old partition-relative signatures are erased while the old device map is still valid; replacing only the GPT would leave old filesystem signatures at their previous offsets. Signature backups supplement, and never replace, the verified file copy and legacy images.

# FIRST DESTRUCTIVE STEP: only after the whole-drive gate and authorization.
mkdir -m 0700 "$MIGRATION_WORK/legacy/signatures"
wipefs --all --backup="$MIGRATION_WORK/legacy/signatures" \
  "$NVME_DISK-part1" "$NVME_DISK-part2" \
  "$NVME_DISK-part3" "$NVME_DISK-part4"

# Replace the entire old GPT with one aligned Linux data partition.
parted --script --align optimal "$NVME_DISK" \
  mklabel gpt \
  mkpart nvme-data ext4 1MiB 100%

partprobe "$NVME_DISK"
udevadm settle --timeout=30

# This selector used to refer to EFI; verify its NEW geometry before use.
NEW_NVME_DATA="$NVME_DISK-part1"
lsblk -b -o NAME,PATH,PKNAME,SIZE,START,PARTTYPE,PARTUUID,FSTYPE,UUID,MOUNTPOINTS "$NVME_DISK"
parted --script "$NVME_DISK" unit B print
parted --script "$NVME_DISK" align-check optimal 1
wipefs --json "$NEW_NVME_DATA"

Stop for inspection before formatting. Prove that the kernel sees GPT and exactly one partition, starting at 1,048,576 bytes and filling the usable region up to GPT's trailing metadata. Verify the new partition's parent device, start, size, Linux data type, and fresh PARTUUID. The -part1 link must resolve to that new partition; old partition 2, 3, and 4 devices and links must be gone. No filesystem signature should remain on the new partition.

partprobe or udev settlement alone is not proof that the kernel accepted the new layout. If rereading fails, a holder remains, a stale link survives, or geometry/identity disagrees, stop before formatting and resolve the mismatch. Do not reuse OLD_NVME_DATA, force the operation, or treat old EFI's -part1 link as sufficient evidence.

This procedure changes the logical layout; it is not a secure erasure of every old data byte.

Create ext4 and update mounts

# DESTRUCTIVE: only after the new single-partition topology gate passes.
mkfs.ext4 -L nvme-data -m 1 "$NEW_NVME_DATA"
blkid "$NEW_NVME_DATA"

Do not add -F to override a mounted-device or identity warning. Record the new filesystem UUID as NEW_EXT4_UUID; do not reuse either old NTFS UUID.

  1. Replace the main-data fstab entry and delete the old recovery entry. The only NVMe filesystem entry is:
UUID=<NEW_EXT4_UUID> /mnt/disk1_part1 ext4 defaults,nofail,nodev,nosuid,x-systemd.device-timeout=15s 0 2

Remove explicit old recovery mount/automount definitions and references. Reload systemd to refresh generated units. Keep the replacement main mount temporarily stopped until its definition and guards are ready; clear its temporary mask before mounting. The old recovery unit must not start again.

nofail allows the machine to boot without the USB disk; explicit service guards must still prohibit fallback writes. Validate with findmnt --verify --verbose, then mount the new data volume through the corrected fstab entry. Verify partition 1, UUID, ext4, and writable state.

  1. Restore the main staging tree with rsync -aHAXSx --numeric-ids. Preserve the existing main-data directory layout. Do not restore EFI/reserved/recovery images to the new NVMe or add their contents as live data; retain those images only in the off-device evidence directory. Do not add a broad deletion option or remove ext4's new lost+found.
  2. Verify restored regular files against the same frozen-source manifest. Compare relative path/type/link inventories; allow only documented ext4 additions such as lost+found.
  3. Before resuming writers, cleanly unmount and run e2fsck -fn "$NEW_NVME_DATA"; a clean result must exit zero. Investigate any other result rather than enabling automatic repair. Remount and recheck the single-partition topology and exact UUID. Filesystem checking must be done unmounted.
  4. Apply the explicit permissions policy below and record intentional metadata differences. Recheck content hashes if any content changed during troubleshooting.

A successful GPT write, mkfs, or mount alone is not restoration acceptance.

7. Permissions, guards, and local service restoration

Permissions policy

NTFS currently synthesizes broadly writable ownership/modes. Do not copy those modes into the final access policy unchanged.

  • Main filesystem root: local owner UID/GID <LOCAL_UID>:<LOCAL_GID>, directory mode 0750. Give nvme-nfs a named access ACL of execute-only (--x) on this root and the shared ancestor directory, with no default share ACL on the main root. Record the effective ACL mask and verify traversal without directory listing; do not assume bind mounts bypass all subtree-check permission requirements.
  • Backups, the original exchange tree, and other private directories: local owner, directories 0700 and ordinary data files 0600; remove ACLs granting share-account access. Review executable files before changing modes.
  • Do not expose the existing exchange folder: it contains private exports and documents. Create shared/exchange as an initially empty curated share; copy only reviewed shareable files there after original-data verification. Preserve the original private files and paths.
  • Create system account nvme-nfs with no login and primary group nvme-share. Record its assigned numeric UID/GID; do not assume they match a client.
  • Selected shared trees (shared/exchange, print, roms): local user owns them, group nvme-share; directories 2770, ordinary non-executable data files 0660, and default group ACLs for collaborative writes.
  • ROMs are exported read-only at the protocol layer, even though the local owner may update them.
  • Add only required local accounts/services to nvme-share and restart the relevant sessions to acquire group membership.
  • Audit game/software executable requirements separately. Avoid a recursive mode command that makes every NTFS file executable or removes executable bits from real software.
  • Bind the NFS identity to shared trees only; it must fail access to backups and the original exchange tree.

Configuration changes to make together

  • /usr/local/libexec/verify-nvme-mounts: require the new main UUID, exact mountpoint, ext4, and writable state. Remove every recovery UUID/mount requirement; only the new ext4 data volume remains.
  • Samba service drop-in: require mnt-disk1_part1.mount only; add BindsTo= and After= for that mount. The actual protected drop-in must be inspected and backed up first. Remove the recovery Samba share and its mount dependency during maintenance: that partition and mount no longer exist after consolidation.
  • ~/.local/bin/home-gdrive-backup.py: update BACKUP_UUID and require ext4 in the existing storage preflight. Preserve its free-space checks, directory containment, writable probe, and open-directory protection.
  • The backup program and health exporter currently uppercase observed UUIDs before comparing them. Normalize both sides, or store the expected ext4 UUID uppercase. A lowercase constant compared with an uppercased actual UUID will fail.
  • ~/.local/bin/export-service-health-metrics.py: update the main UUID and filesystem expectation; remove the recovery mount from current MOUNTS expectations entirely and require ext4 for the new main volume. Regenerate current exporter state/metrics so removed recovery labels stop being emitted; preserve historical telemetry and private evidence.
  • ~/dev/qbittorrent-vpn/up.sh: validate exact mount, new UUID, ext4, and writable state before creating downloads directories or starting containers. Replace Docker volume syntax that creates missing host directories with --mount type=bind. Keep torrents/downloads as the download path.
  • Update the active revive-nvme-smb skill and scripts/revive_nvme_smb.sh under ~/.codex/skills/revive-nvme-smb before maintenance ends. They currently require both old NTFS UUIDs and revive the retired recovery/full-volume shares. Replace those active procedures with the single ext4 UUID guard and selected-share/NFS recovery instructions; they must never recreate the removed partition/mount or re-enable the retired broad share. Instrument any revised critical device/network script through the existing OTel integration.
  • Search other application launchers, cron jobs, unit files, skills, and backup configuration for old UUIDs, partition numbers, the retired recovery mount, and NTFS-only assumptions. Update only active relevant consumers; preserve historical evidence as history.
  • Archive the old NTFS integrity finding privately. Clear only that resolved active warning after copy, restoration, and filesystem checks pass. Make any remaining filesystem-check alert text filesystem-neutral.

Restore and verify local consumers

  1. Remove temporary masks after corrected configuration is loaded. Verify mount guards positively with the disk mounted and negatively during a controlled unmounted maintenance check. Guard failure must occur before writing or serving an underlying microSD directory.
  2. Run the existing health exporter and inspect its output and automation snapshot.
  3. Restore Samba only if needed for the compatibility phase. Before restart, disable the old full-volume data share and recovery share. Configure only curated shared/exchange, print, and read-only ROM shares, restricted to the same approved client addresses. Preserve existing guest/forced-local-user behavior only for these selected trees, force group nvme-share, and use matching create/directory permissions. Validate testparm and real client access.   4. Check RetroArch ROM paths, Kodi local sources, and torrent bind paths without starting applications that were previously stopped. If a consumer needs an actual run to validate, schedule its bounded acceptance check.
  5. Run the backup storage preflight under the existing backup service identity. Its --check-storage option writes a probe, state, and metrics; this belongs to execution validation. --check-drive can create remote folders and is not a harmless read-only check.
  6. Complete one fresh backup with --skip-retention, using the existing instrumented backup integration under its normal user identity, and inspect local integrity plus fresh Drive-verification results. 8. Phase D — NFSv4 server and client transition

Start after local ext4 acceptance. Record explicit authorization for the persistent NFS server during migration execution; no NFS daemon or timer is created by this planning task.

Network and identity choices

Use the wired server address, reserved in DHCP, and an explicit list of approved client addresses. Reconfirm the recorded <WIRED_SERVER_ADDRESS> address. Never export to * or the entire LAN by default.

Use sec=sys only on the trusted LAN. It does not encrypt or cryptographically authenticate clients. Requests to these shares are mapped with all_squash to the dedicated nvme-nfs identity; also retain explicit root_squash. This mirrors single-owner shared-file behavior without accepting arbitrary client-supplied owner IDs. Per-user ownership or access over an untrusted network requires a separate authenticated/encrypted design.

Install nfs-kernel-server on the server and nfs-common on clients only after blocking package-triggered serving until configuration is complete. Configure /etc/nfs.conf.d/nvme.conf:

[nfsd]
vers3=n
vers4=y
vers4.0=n
vers4.1=y
vers4.2=y
udp=n
tcp=y

Allow TCP 2049 only from the approved clients on the intended interface. Inspect existing firewall policy before changing it; preserve administrative access. Verify actual protocol versions and listeners after startup rather than assuming package defaults.

Export layout and mount safety

Create root-owned /srv/nfs/nvme mode 0755 as the NFSv4 pseudoroot. Do not bind or export the whole data volume. Its children are separate bind mounts:

  • /srv/nfs/nvme/exchange → /mnt/disk1_part1/shared/exchange, read/write.
  • /srv/nfs/nvme/print → /mnt/disk1_part1/print, read/write.
  • /srv/nfs/nvme/roms → /mnt/disk1_part1/roms, read-only.

Create only these approved exports. Games, installers, torrents, backups, the private exchange tree, and off-device legacy images are not exported. Add a media export only after identifying the actual media subdirectory and reviewing its contents.

Use native systemd bind-mount units named for their destination paths. Each requires, follows, and binds its lifetime to mnt-disk1_part1.mount. Keep the underlying unmounted child directories root-owned mode 0000.

Example srv-nfs-nvme-exchange.mount:

[Unit]
Description=Curated NVMe exchange bind
Requires=mnt-disk1_part1.mount
After=mnt-disk1_part1.mount
BindsTo=mnt-disk1_part1.mount

[Mount]
What=/mnt/disk1_part1/shared/exchange
Where=/srv/nfs/nvme/exchange
Type=none
Options=bind

Use analogous units for print and ROMs; use Options=bind,ro for ROMs and verify the effective bind mount is read-only.

The NFS server unit must require and follow all bind mounts and a fresh pre-export guard oneshot. Bind its lifetime to the main mount and bind mounts. The guard must verify the new UUID, ext4, and the exact FSROOT of each child (/shared/exchange, /print, /roms). A mere existing directory or matching path prefix is insufficient.

Make the guard a required dependency ordered before the NFS server, rather than appending it after packaged ExecStartPre commands that may already run exportfs. Avoid RemainAfterExit so the guard is checked on each start, and do not bind server lifetime to the completed inactive oneshot. Inspect the installed Debian unit names and full startup chain before applying drop-ins.

Export template

Create /etc/exports.d/nvme.exports. Substitute an actual approved client address and the dedicated server-side numeric UID/GID; repeat host entries for each approved client. Placeholder text is not a runnable configuration.

/srv/nfs/nvme CLIENT_IP(ro,fsid=0,sync,sec=sys,root_squash,all_squash,anonuid=NFS_UID,anongid=SHARE_GID,subtree_check,mountpoint=/mnt/disk1_part1)
/srv/nfs/nvme/exchange CLIENT_IP(rw,fsid=101,sync,sec=sys,root_squash,all_squash,anonuid=NFS_UID,anongid=SHARE_GID,subtree_check,mountpoint)
/srv/nfs/nvme/print CLIENT_IP(rw,fsid=102,sync,sec=sys,root_squash,all_squash,anonuid=NFS_UID,anongid=SHARE_GID,subtree_check,mountpoint)
/srv/nfs/nvme/roms CLIENT_IP(ro,fsid=103,sync,sec=sys,root_squash,all_squash,anonuid=NFS_UID,anongid=SHARE_GID,subtree_check,mountpoint)

No crossmnt, no_root_squash, insecure, or whole-volume export.

A bind mount is not a distinct security filesystem. Keep subtree_check because these are subdirectories of a filesystem that also holds private data; exercise rename/open-file cases because subtree checking can complicate filehandles. The dedicated squashed identity must lack permissions on private trees even if a client guesses a filehandle. This is access control for trusted approved clients, not isolation against arbitrary hostile hosts.

Client mount and transition

For each client, save the original SMB mount/app configuration, install its NFS client package, and first mount to a temporary test location. Use NFSv4.2 over TCP with hard, _netdev, nosuid, and nodev; confirm version 4.1 compatibility only if the client cannot use 4.2.

SERVER:/exchange /mnt/nvme-exchange nfs vers=4.2,proto=tcp,hard,_netdev,nosuid,nodev,nofail,x-systemd.automount,x-systemd.mount-timeout=30s 0 0

Use matching lines for print and ROMs with ro for ROMs. The mount timeout bounds the initial mount attempt, not ongoing operations: a hard mount can wait during a server outage. Do not use soft to make write operations fail quickly.

Preserve application-facing client paths when switching away from SMB, and ensure clients do not write into empty local mount directories. Each writer needs an actual mount/source guard before directory creation. Stop the application before unmounting its old share.

Client acceptance for every approved host:

  • Confirm mounted server, export, NFS version, and read/write mode.
  • Create, read, checksum, rename, and remove a test file in exchange/print as the intended application user.
  • Confirm server-side ownership maps to nvme-nfs:nvme-share, including a client-root write; client root must never create server-root-owned files.
  • Confirm ROM reads succeed and writes fail.
  • Confirm the private backup and original exchange directories cannot be mounted or accessed, including attempts using client root or a claimed server-owner UID.
  • Verify symlink and renamed/open-file behavior; test any application requiring locks.
  • Prove a non-allowlisted client cannot mount.
  • During a scheduled idle test, verify loss of the main mount or a bind mount prevents serving; restore the correct mount, restart the guarded server, and verify recovery. Do not unplug a busy drive or interrupt active jobs.

The old broad SMB data share is removed before compatibility restart. After all clients pass and a seven-day observation window completes, retire the selected SMB compatibility shares. Retire smbd/nmbd/winbind only if no other use is found. Preserve their configuration for rollback and update service/TCP health expectations at the same time.

9. Monitoring, reboot acceptance, and recovery

Monitoring and instrumentation

Keep the existing metrics exporter and existing scheduling. Update expected main UUID/type, remove the retired recovery mount from current expectations, and switch Samba service/TCP expectations to NFS only when SMB is retired. NFS health needs both the service/listener and correct mounted/exported data, not merely an open TCP 2049 port.

Capture wrong UUID, wrong filesystem, missing data mount, missing bind, unexpected export, copy/hash failure, and backup failure in the Microserver automation snapshot and Morning Digest. Preserve other findings when resolving the old NTFS warning.

Instrument the required nvme-nfs-guard service before deployment with stable OTEL_SERVICE_NAME=nvme-nfs-guard, the local wrapper/bootstrap integration, failure metrics, and automation snapshot visibility. Mount validation must remain fail-closed even when telemetry export is unavailable; a telemetry error cannot turn a failed mount check into success. If execution is wrapped in an additional script with network or device-control paths, instrument that script before use: stable OTEL_SERVICE_NAME=nvme-migration, the existing otel-python-cron.sh/automation_otel_bootstrap integration, every-third-API-call sampling, every failing call/job recorded, atomic phase/success/duration metrics under ~/.local/state/node-textfile, and failure visibility through the existing automation summary consumed by Morning Digest. No new scheduler is needed. Raw checksums, filenames, identities, and private data must not become metric labels or public reports.

Reboot and completion gates

Reboot only during an agreed idle window after checking printer, ComfyUI, backup, and other active work. Then verify:

  1. The host boots from the microSD. The NVMe has GPT and exactly one physical partition, partition 1, with the new UUID/ext4 mounted at the original main-data path. The old recovery mount, fstab entry, share, unit dependencies, and current health expectation are absent. No service wrote into the underlying microSD mountpoint.
  2. Restored data verification and the offline filesystem check passed before writers resumed.
  3. Ownership and permissions match the deliberate policy; local application paths work.
  4. One fresh backup and remote-integrity verification pass; the timer is restored without overlapping jobs.
  5. NFS exports, firewall allowlist, positive/negative client tests, and mount guards pass.
  6. The automation snapshot and Morning Digest report the correct mount/service state, without a stale resolved NTFS warning or fabricated healthy result.

Retain the verified staging copy until all gates pass, SMB has completed its seven-day transition, and at least one fresh post-migration backup is confirmed. Then obtain a separate retention decision before deleting it. Existing home-only backups still do not protect ROMs, games, exchange, or print data; document that coverage gap and design a separate backup policy if those data require ongoing protection. The migration copy is temporary recovery material, not that long-term policy.

Recovery by failure stage

  • Before any signature erasure or repartitioning: leave the original layout and NTFS filesystems intact. If safe, remount it in the prior state and restore saved service configuration/states. Do not bring inconsistent NTFS back read/write merely to shorten an outage.
  • After signature erasure/repartitioning, before restoration acceptance: stop writers and shares. Repair/recreate ext4 as appropriate and restore from the verified staging tree again. Preserve the immutable source manifest. Restoring only the old GPT or saved signature bytes cannot recover overwritten filesystems/data. Do not assume a quick partition-table rollback is safe.
  • After ext4 local success, NFS failure: disable the failed NFS exports and restore selected SMB access over ext4 using the saved client configuration. Keep private data protected. There is no need to return to NTFS.
  • Actual return to the former Windows/NTFS layout: separately destructive and not part of normal recovery. A full original raw disk image, if explicitly taken, can restore the original arrangement. Otherwise reconstruction requires the saved GPT, old EFI/reserved/recovery images, creation of a replacement main NTFS filesystem at the correct bounds, and restoration of the verified main files. File copies and small-partition images do not recreate the original main NTFS metadata. Stop for a dedicated recovery procedure rather than replaying old partition offsets onto live ext4.
  • microSD/staging failure after destructive work begins: the only other recovery copy is an independently verified external copy if one was made. Home-only cloud backups do not restore the entire NVMe. This residual risk is why a second device copy is preferred.
  • Unreadable data or unstable hardware: stop rather than repeatedly remounting or clearing flags. Reassess recovery/imaging on separate storage. Escalate any unresolved fix after 20 concrete attempts through the user's ntfy procedure with the last error and evidence.
