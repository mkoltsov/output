01 / What should improve

Ten decisions with evidence.

P1 means address in the first maintenance sequence. P2 means a planned reliability improvement. Priority is an audit judgement, not evidence of compromise or a claim that every component is broken.

01P1

Updates do not currently patch the host

The enabled APT timer path has effective periodic intervals of zero, and unattended-upgrades is absent. Fresh isolated signed indexes found 314 upgrade candidates, including 92 with a security origin. These are package counts, not a CVE count.

Change

Verify recovery, stage updates by application dependency, then perform attended reboot acceptance. Monitor index age and actual patch outcomes.

What must pass

Signed metadata and expected package versions; applications, remote access, USB, UPS, mounts and SMB/NFS pass after maintenance.

02P1

One service inherits authority for unrelated systems

Quest starts through broad shell configuration. Key-name-only inspection confirmed unrelated router, Spotify and downloader secrets in its environment. The operator also has Docker and sudo/device authority; the saved administrative password is readable by that identity, although not exported to Quest.

Change

Start with per-service environment allowlists, then separate UIDs/groups/filesystem access. Keep root-owned narrow storage helpers; do not grant a service the whole home for metrics.

What must pass

Under the real service identity, required operations succeed and unrelated secrets, browser profiles, Docker socket and devices are denied.

03P1

Browser containment is weaker than it needs to be

The configured Chromium launcher disables its sandbox and allows all CDP origins; CDP binds to loopback. User namespace prerequisites work, but full sandbox-compatible workflow validation has not been done. The browser seen in the audit was started by report preview work.

Change

Validate a separate private profile with normal sandboxing and narrow origins, then give browser work its own authority and deliberate session-recovery policy.

What must pass

Broker workflows and actual sandbox state pass; CDP stays local; active leases and user tabs are preserved.

04P1

Local web access needs clearer authentication and client boundaries

Quest and piano respond without login on all IPv4 interfaces. Quest exposes write handlers with Origin checks; those checks do not authenticate a client. Piano’s demonstrated issue is unauthenticated static/source access; no write handler was observed. The live firewall has the five sharing restrictions but otherwise accepts host INPUT.

Change

Define intended clients, require appropriate authentication/access restrictions and serve only explicit assets. Include Ethernet, Wi-Fi and IPv6 in acceptance.

What must pass

Intended devices work; unauthorized reads/writes and source/config retrieval are denied. No external exposure or exploit is asserted by this audit.

05P1

Good backup integrity is incomplete recovery

The latest 5.505 GB archive passed a full local checksum/decompression check and representative script/timer/SQLite restores. Fresh cloud metadata matches sizes/hashes and owner-only permissions. The archive is credential-bearing, unencrypted and home-only; only two remote generations remain.

Change

Add independently recoverable encryption, system/data coverage, application-consistent exports and longer retention. Fix the stale aggregate verification timestamp. Preserve current copies until the replacement path passes.

What must pass

Restore required applications and selected data without the original host, including a fresh cloud download and documented boot recovery.

06P1

Several automations report process success without completing the task

Recorded examples include Spotify entitlement failures caught before exit 0, Digest exhausted-retry state becoming green, and a printer send failure being consumed. The release watcher has 106 consecutive recorded job errors; weekly meal publication has 22 recorded failures, which do not establish whether its earlier email stage failed.

Change

Use typed success/partial/blocked/failed states plus a durable outbox for external effects. Fix the demonstrated defects before adding more automation.

What must pass

The 18 isolated failure scenarios described below become regression cases; no swallowed failure, lost work or duplicate delivery in the relevant fixture.

07P1

Telegram expansion needs a separate, durable reader

The current bot is not a member of the requested forum and monitors a different configured chat. Source/probes show cursor, edit and crash-replay problems. Broadening the existing privileged dispatch path would expand account/host authority.

Change

For accessible history use a separately authorized MTProto user session; isolate ingestion from owner controls, commit inbox/cursors transactionally and deliver through an outbox.

What must pass

One authorized source passes topic/history/live reconciliation, edit/delete handling and restart tests; group events cannot invoke privileged tools.

08P2

Seven alerts provide partial coverage

The stack has one Grafana-managed, four Loki-managed and two Prometheus-managed rules. They cover power logs, router/presence errors, Telegram log absence, selected cron error text, combined CPU/memory pressure and host-metric absence. They do not form a complete per-job success/deadline registry.

Change

Retain working rules and add domain-specific freshness/outcome alerts for the reconciled job inventory, verified backups, UPS and transport failure. Distinguish data absence from domain failure.

What must pass

Safe fixture failures reach the snapshot, an appropriate evaluated alert and a verified notification path; no live event/notification was injected during this audit.

09P2

Network and storage assumptions need lifecycle tests

A retained Ethernet event shows 343 seconds without carrier plus short flaps; cause is unverified. Wi-Fi may be a useful fallback. Hardcoded service addresses depend on router reservations. Docker restart policy can bypass the stack startup preflight; a disk spill was not demonstrated.

Change

Verify reservations and intentional bindings, correlate link events, and exercise missing/wrong storage and daemon-restart behavior in isolated fixtures.

What must pass

Expected failover and intended client reachability pass; no consumer can silently use the wrong storage. Keep the working remote session available.

10P2

Recovery and provenance need sharper boundaries

The hardware watchdog is already active; bounded Docker logs, curated shares and stable process metrics are already configured. UPS battery/shutdown behavior, cloud-content restore, bridge SMART/TRIM and sandbox compatibility remain unproven. Mutable container/MCP dependencies obscure reproducibility.

Change

Preserve the working controls. Record accepted versions/digests and reversible update procedures; test only the specific remaining recovery/compatibility gaps.

What must pass

The acceptance record states exactly what was restored or exercised, what authority was used and what remains unknown.

04 / What success really means

Follow the useful result.

The machine can be up, the command can exit zero, the API can return 200, and the task can still be incomplete. These boundaries need independent state.

01 / SCHEDULEWas it launched on time?

Owner, schedule, timeout, overlap policy and last start.

02 / SOURCEDid valid data arrive?

Authorization, parser/schema, freshness and coverage.

03 / BUSINESSWas the intended result achieved?

Per-section/target/device outcome, durable state and readback.

04 / DELIVERYDid the result reach its destination?

Outbox state, verified publication/send and ambiguous effects.

Observed failure signatures

  • Release watcher: 106 trailing recorded nonzero jobs. A current HTTP 200 response contains an anti-bot challenge; this does not prove the cause of every historical failure.
  • Weekly meal publication: 22 trailing recorded publication failures. These records do not establish whether the email stage failed. A dry run reproduces an attempt to stage ignored private state. Never solve this by force-adding that state.
  • Spotify: recorded Premium-required 403 is caught before exit zero. Exact current account entitlement was not rechecked.
  • Digest, presence, watchdog and print notifier: isolated fixtures reproduce lost state, misleading completion or unsafe retry decisions.

18 concrete offline scenarios

Six shared/monitor probes cover failed-action handling, crash replay, corrupt JSON startup, sensitive query retention in telemetry, telemetry errors masking API errors and unsafe metric-label truncation.

Three Telegram probes cover edit/new conflation, an uncleared owner queue and premature batch cursor persistence. Nine automation probes cover presence unknown/away, lost sends, exhausted retries, retry context/timeouts, router recovery decisions, concurrent circuit state, Calendar pagination, Tasks pagination and printer notifications.

These are fault-reproduction fixtures using temporary state and stubbed dependencies, not production actions. They are not a comprehensive test suite and were not “fixed” during this research.
