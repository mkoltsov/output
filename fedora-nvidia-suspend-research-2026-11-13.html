What the computer itself establishes

The current system is Fedora 44 Workstation, kernel 7.3.3-200.fc44, GNOME Shell 50.6, Mutter 50.6-2, systemd 259.10, and NVIDIA 620.70.06 open modules. The desktop runs on Wayland. Hardware is a ZOTAC MAGNUS ONE with an Intel i5-10400, nominal 64 GB RAM, and RTX 5060 Ti with nominal 16 GB VRAM. Two NVIDIA DisplayPort outputs are connected; saved configuration uses 2560 × 1440 at approximately 59.95 Hz and scale 1. No rotation or HDR mode was specified in that saved configuration.

Deep/S3 is selected. Active driver parameters show automatic video-memory preservation (PreserveVideoMemoryAllocations=2), kernel suspend notifications enabled, and an empty temporary backing-path value. The installed NVIDIA sleep services check the notifier mode before running the older userspace hooks; skipping those hooks under the current mode is expected. Their presence or enabled state does not demonstrate that a sleep cycle has worked.

The NVIDIA package supplies SYSTEMD_SLEEP_FREEZE_USER_SESSIONS=false. Automatic idle suspend is disabled for mains and battery. Sleep targets remain available and the short power-button action remains suspend. This distinction matters because several recorded attempts were power-button requests, rather than an idle timeout.

Historical transitions

Five deep-suspend attempts in August used kernel 7.1.8 and NVIDIA 610.57.04. The latest retained attempt, on 26 October, used kernel 7.2.10 and NVIDIA 615.71.09. None has a corresponding recorded resume completion. Journals stop at, or immediately after, sleep entry. This is consistent with the reported nonwake, but cannot identify whether the machine failed while entering sleep, failed to wake in firmware, lost the GPU during recovery, or was later powered off before more logs persisted.

One August transition has an additional graphics clue: NVIDIA DRM buffer-allocation failures and GNOME front-buffer errors occurred immediately before or during the suspend transition. That strengthens the case for investigating the graphics stack. The other transitions, including October, lack a decisive nearby GPU, PCIe, or SELinux error. An earlier GPU error hours before one attempt is not sufficient to assign its cause.

The current 620.70.06 packages were installed after the last retained attempt. There is no fresh suspend test on this stack. A separate early-boot kernel W^X warning is also present, but no evidence links it to the historical sleep failures.

What the fixes establish

The current stack is meaningfully different from the failing one

The Fedora SELinux report is especially relevant because it describes the exact interface transition NVIDIA made: VRAM preservation invoked by a kernel notifier runs under systemd's restrictive sleep context. NVIDIA confirmed a workaround, and the packaged driver changelog identifies its release. This is stronger evidence than a generic forum suggestion. It still does not prove the October event was an SELinux denial: the retained local journal has no corresponding denial near that transition. Fedora issue and developer discussion.

Current Mutter also contains earlier fixes for NVIDIA freezes and an external-monitor hotplug hang. Its tagged 50.6 release history confirms those changes, but does not identify a universal NVIDIA suspend correction. Upgrading a compositor does not automatically settle firmware wake, driver VRAM restoration, PCIe recovery, and display reconfiguration at once. Official Mutter release history.

Black screen, frozen desktop, and failed S3 are different outcomes

A machine can remain fully awake while its monitors are in standby. It can resume successfully but leave the display engine wedged. It can restore the desktop and fail later when a new modeset occurs. Or it can fail before entering S3 at all. The historical logs on this host do not contain enough transition detail to select one mechanism for every incident. The computer's reported inability to wake should be treated as a real operational failure while that distinction remains unresolved.

Public reports demonstrate all of these shapes. Some latest-version reports have a working management interface even when the desktop or GPU clients have failed. Consequently, a responsive nvidia-smi alone cannot certify healthy display recovery or CUDA execution. Conversely, failed SSH after wake could reflect failed networking rather than a dead kernel.

Several popular workarounds are poor first choices here

  • Proprietary modules or disabling GSP: NVIDIA documents that Blackwell requires the open-module flavor. Workarounds aimed at older architectures are not interchangeable with this RTX 5060 Ti. NVIDIA architecture support.
  • Disabling video-memory preservation: may discard Vulkan/CUDA application state. A suspended machine that returns with broken GPU applications has not passed a useful reliability test.
  • Removing the session no-freeze override: the NVIDIA package deliberately supplies it. Systemd's own release notes describe the driver compatibility problem. Do not remove it solely because systemd prints a warning about unfrozen sessions. Systemd 256 release notes.
  • Blindly choosing s2idle: the platform does not advertise NVIDIA S0ix support. That does not make every s2idle test impossible, but it removes the basis for promising equivalent low-power behavior or a reliable cure.
  • Blindly setting disk backing: it can reduce RAM pressure, but filesystem access and SELinux must also work. The separate explicit-path Fedora report prevents calling that setting a universal fix.
  • Switching to X11: one older report used it as a control. It does not establish that an X11 route is installed, supported by this desktop, or necessary to solve the current failure.

A useful validation plan, when explicitly scheduled

No suspend test was performed. The ComfyUI queue was checked and was empty at the start of this research; that observation expires as soon as another job starts. Saved work and a fresh queue check remain prerequisites for any later disruptive test.

  1. Prevent accidental testing. Keep idle suspend off. Consider changing the short power-button action to an interactive prompt, since it currently invokes the historically failing path. This is a recommendation only; it was not changed.
  2. Start with the current configuration. Retain notifier-based preservation and the package's session override. Establish an idle baseline with both displays attached. Record the chosen wake method and observe the actual power/sleep behavior.
  3. Observe from another machine where possible. Arrange remote observation before sleep, and collect transition logs after wake. A remote connection is a diagnostic aid, not proof that every subsystem recovered. Avoid publishing raw diagnostic archives containing machine identifiers.
  4. Test both short and longer sleeps, then repeated cycles. A single clean wake cannot exclude intermittent behavior. After wake, verify both displays, input, desktop interaction, an actual CUDA allocation/computation, and eventually a representative short ComfyUI run. Continue watching for delayed GPU faults.
  5. If it fails, classify before changing settings. Determine whether it reached S3, whether the kernel resumed, whether networking returned, and whether display and compute paths work separately. Kernel PM test stages can isolate freezer/device/platform failures but are themselves disruptive. Kernel debugging procedure.
  6. Compare one variable at a time. An older-kernel comparison must retain the same NVIDIA driver. Locally, the installed 7.2.13 kernel currently has a 615.71.09 NVIDIA module while 7.3.3 has 620.70.06. Merely selecting the older kernel would change both variables. Matching modules must be prepared and verified before a controlled comparison. The older kernel is not a known-good suspend baseline.

If evidence specifically shows insufficient VRAM backing capacity, a disk-backed temporary path is a supported candidate. Current default anonymous backing relies on RAM/swap; it is intentional. NVIDIA recommends capacity based on total VRAM plus 5%, roughly 17 GiB for this card. The inspected disk-backed temporary filesystem had about 53 GiB available, but free space alone does not establish access permission or resolve a display/firmware deadlock. Version-matched NVIDIA power-management documentation.

What remains unknown

There is no matched local post-failure stack trace, no verified current-stack sleep cycle, and no live observation of firmware wake. Privileged archived audit/pstore data were not fully accessible. The board BIOS dates from 2022; availability of a newer exact-board firmware and any applicable sleep fix were not verified. Age alone is not a diagnosis or a reason to flash it.

GNOME issue status and descriptions were verified using its public API because the normal tracker UI was unreliable. Some comments and merge-request endpoints were unavailable; developer endorsement of report-body hypotheses was not assumed. Public driver download pages did not reliably render their changelogs, so the installed NVIDIA changelog was also inspected directly. No issue was filed, no message was sent to maintainers, and no package was installed.

The conclusion is deliberately narrower than either “suspend is safe” or “the new driver definitely fails.” There is credible evidence of improvement since the last attempt, close historical bug matches, and unresolved reports in related paths. A supervised, instrumented baseline on this exact machine is the missing evidence.
