Comparison windows

The boundary used here is the current backend process start at 15:40:59 Eastern. This process-start timestamp is a candidate activation boundary; it is not, by itself, proof of the first-ever remote-integration enable time.

Before: 14:20–15:40. Active period: 15:55–17:15. Each comparison uses 17 equally spaced samples. The first post-start rate sample is delayed until 15:55 so its trailing ten-minute window is entirely after the start. The later interval is 16:40–17:15, eight samples. Previous-day comparisons use the same local clock times.

Six prior days’ corresponding CPU means ranged from about 6.1% to 6.5%, below the current active-period mean. Earlier ordinary workloads nevertheless produced individual peaks substantially larger than those observed in this session. The additional workload is observable; persistent integration overhead is not isolated.

Codex footprint and current capacity

The observed Codex process-group CPU counter corresponds to approximately 0.04% of total four-core capacity before, 0.91% during the active period, and 0.24% later. These figures use counter endpoint differences divided by elapsed time and four cores. They measure sampled process-group CPU, not the entire cost of tasks launched by Codex; short-lived children can escape process sampling.

Grouped Codex resident memory averaged approximately 174 MB before and 424 MB after. In the later interval it averaged 390 MB. Group RSS is not interchangeable with host memory used and can count shared pages in multiple processes.

At the final historical sample, approximately 3.24 GB remained available. Existing swap occupancy increased only slightly, and the later interval had no measured swap-out activity. All recorded undervoltage and throttling flags were zero throughout the queried seven-day history.

Attribution and limits

Connection handling, active Codex tasks, repository cloning, audio validation, test execution, and publishing occurred during the same period. Background scheduled jobs also run on this server. This comparison cannot separate idle connection overhead from those task costs, and the investigation did not stop or restart the integration to conduct a controlled experiment.

CPU and disk rates use ten-minute lookbacks, evaluated every five minutes. The six headline series each contain 2,017 finite samples across seven days, with no missing evaluation points. Such completeness does not independently prove every raw scrape arrived, and five-minute evaluation can miss shorter spikes. No confidence interval or causal treatment effect is claimed.

Metric definitions and evidence
  • CPU busy: 100 × (1 − mean idle CPU-counter rate), normalized across all CPU cores. It includes I/O wait.
  • Memory used: total memory minus available memory, converted to decimal MB.
  • System-disk writes and busy time: rates from the operating-system disk counters, not data-volume counters.
  • Host load is the Linux one-minute load average, shown against a four-core host.
  • Temperature is the thermal-zone reading in Celsius.
  • Prometheus metrics: node_cpu_seconds_total, node_load1, node_memory_MemAvailable_bytes, node_disk_written_bytes_total, node_disk_io_time_seconds_total, node_thermal_zone_temp, and grouped microserver_process_rss_bytes.

Queries were made against the configured Grafana Cloud Prometheus source. Raw responses, credentials, host identifiers, addresses, private URLs, process arguments, and user content are excluded from this public report.
