Scalper automation reliability audit

25 findings: 10 P1, 12 P2, 3 P3. Priorities describe repair urgency, not proven production incidents.

Review of the general software pipeline: search responses, evidence validation, state, notifications, publishing, scheduling and downstream reporting.

Evidence boundary: Observed means recorded operational state. Reproduced means a controlled offline diagnostic confirmed the behavior. Inspected means the code permits the failure but no production occurrence was demonstrated. The two prior live checks returned zero raw candidates; the validator defects are not proven causes of those empty results. No new live inventory searches were run for this audit.

Validation: 29 existing generic filter/browser tests and 2 automation-health tests passed. Additional mocked diagnostics reproduced gaps those tests miss. Existing source changes were preserved. This is a review and repair proposal, not an implementation.

This public report contains generalized technical findings only. Personal target details, exact private destinations, raw configuration, logs, credentials and private source data were excluded.

Suggested repair order

Estimated size: S = a localized change plus targeted checks; M = several components and failure-path tests; L = an architectural change or a broad verification contract. These are relative engineering estimates, not a measured schedule. Start with the low-effort safeguards: configuration validation, diagnostic isolation, correct disabled-delivery state and status publication.

  1. Make outcomes truthful: validate output/configuration, record every target and configuration revision, isolate diagnostic output, expose search and publication failures.
  2. Make delivery and publication durable: checkpoint acknowledgements, retain retryable pending work, use isolated Git publication and acknowledge remote success separately.
  3. Make verification reliable: repair browser transport/navigation, require selected-listing evidence and enforce public-network and pricing boundaries for ordinary products.
  4. Measure and simplify: export coverage/stage metrics, bound job effort, improve meaningful scenario tests and align consumers.

Do not weaken availability checks or price requirements to increase the result count. A genuine completed empty scan is a valid outcome.

P1 M Search output can silently become a successful empty scan Reproduced scalper.py:585, 2460 An empty object is accepted. The prose fallback can select a nested deal object instead of the enclosing result. Null or wrongly typed deals can abort later processing. Validate a versioned result schema, expected target ID, timestamps, list types and every candidate. Record failed, blocked, incomplete and completed-empty outcomes separately. Malformed output reports an error; nested JSON is never mistaken for the top-level result; a bad candidate does not prevent the next target.
P1 M Reported target coverage is not tied to the completed scan Observed + inspected scalper.py:2448; digest_section_pages.py:429 The current configuration has 3 targets while the latest published scan contains 1. Failed targets disappear. Current configuration is displayed beside an older scan without a pending status. Record configuration hash/revision, configured IDs, attempted IDs and a result for every selected target. Newly added targets remain pending until a completed attempt. Change configuration after a scan: new targets display pending. A timed-out target remains visible as failed rather than disappearing.
P1 L One notification failure stops remaining searches Reproduced scalper.py:2536, 2567 Delivery exceptions escape the target loop. Successful earlier acknowledgements exist only in memory until the entire run completes; restart can resend them. Separate discovery from delivery; use a durable outbox; checkpoint confirmed acknowledgements; isolate each delivery error and finalize run status. First delivery succeeds and second fails: later targets are still checked; acknowledged items do not resend; failed delivery remains pending.
P1 S Disabled notifications are recorded as delivered Reproduced scalper.py:2534 A run without a notification destination writes notified records despite making zero delivery requests. Enabling delivery afterward suppresses those offers. Track seen, eligible, queued and acknowledged states separately. Mark delivered only after a successful acknowledgement. Scan with delivery disabled, enable delivery, repeat the same ordinary consumer item: exactly one notification is sent.
P1 M Publication can commit unrelated work and mutate a development checkout Inspected scalper.py:2353 The publisher rebases/autostashes the shared checkout, stages output, commits the entire index and pushes current HEAD to main. Existing staged changes or another branch can be included. Use an isolated publication checkout or worktree with an explicit branch and output-only commit. Keep the developer checkout untouched. Staged and unstaged source changes plus a non-main branch remain byte-identical and uncommitted by publication.
P1 M Failed publication is not durably retried Inspected + reproduced signature scalper.py:2380, 2551, 2562 Local output and success state are updated before pushing. A failed push leaves the next identical result looking unchanged; retry may wait up to the 12-hour heartbeat. State can say success while the job wrapper says failure. Store scan, notification and publication outcomes independently. Compare with the last acknowledged remote publication, retain a pending retry and verify both branches and served content. Inject a branch push failure. An identical next scan retries publication immediately and reports the failed publication separately from the successful scan.
P1 M Browser transport can hang or corrupt valid messages Reproduced scalper.py:1109, 1140 The custom WebSocket assumes complete header reads, discards frames coalesced with the handshake, mishandles fragmented messages and repeatedly reads immediate EOF in a truncated payload. Use a maintained transport already supported by the environment, or implement buffered exact reads, fragmentation, EOF handling, frame limits and absolute deadlines. Split all header boundaries, coalesce handshake plus frame, fragment text, send ping and truncate payload: deterministic result or bounded failure with cleanup.
P1 L Generic listing checks can accept non-buyable or wrong pages Reproduced scalper.py:1030, 1278 Generic checks can accept a non-HTML response, a home-page redirect, archived documentation with one matching title word, or a bare Sold status. Positive purchase/contact, price and stock evidence is not required. Use a common verification contract for ordinary products: final URL/listing identity, selected variant, current price, explicit availability and enabled purchase/contact action. Preserve uncertainty. Documentation, homepage/search redirect, disabled cart, sold listing and wrong variant all fail; a genuine exact listing passes with retained evidence.
P1 M Untrusted URLs can reach local or non-web destinations Normalization reproduced; access risk inspected scalper.py:1702, 1007, 1228 Local-file and loopback URLs normalize successfully. The fetch/navigation path lacks a public-network boundary, including redirects and DNS resolution. No local resource was fetched during this audit. Allow explicit web schemes; reject URL credentials and local/private/link-local/reserved addresses across IPv4/IPv6. Recheck DNS and every redirect; enforce controlled egress. Non-web schemes, private DNS answers, encoded loopback, IPv6 local addresses and redirects into internal networks are rejected before access.
P1 M Ordinary pricing accepts contradictory or missing amounts Reproduced scalper.py:1740, 1753 An item costing 150 plus delivery 20 can pass a ceiling of 100 when the supplied total is 50. Negative totals, missing item price, unknown shipping as zero and missing availability promoted to available also pass. Use one bounded nonnegative decimal/cents contract; recompute totals; reject contradictions; keep unknown shipping and availability explicit until verified. Contradictory totals, negatives and missing prices fail; unknown delivery is not free; exact ceiling and verified zero-cost delivery behave as specified.
P2 L Whole-page and commentary matching creates false rejection and false acceptance Reproduced scalper.py:630, 984, 1037, 1263 Unrelated recommendations or hidden out-of-stock text reject a good item. A normal reCAPTCHA footer looks blocked. Commentary saying not damaged is rejected; the desired model mentioned only in a comparison can qualify the wrong item. Scope identity and condition to selected-item facts; parse status fields individually; use visible product DOM and actual challenge indicators; treat commentary separately. Unrelated sold recommendations, hidden text and a normal contact footer do not invalidate a verified item; real sold/challenge status and wrong identity still fail.
P2 M Browser navigation can verify stale DOM Reproduced scalper.py:1228 Navigation errorText is ignored. Readiness only requires a nonempty interactive/complete document; the routine can return an older page or a partially hydrated page after timeout. Check navigation errors; bind the result to the navigated frame/loader and final URL; wait for product evidence under one deadline and fail when it expires. DNS failure with old DOM, redirected page, slow hydration and never-ready document cannot be mistaken for a completed exact-listing verification.
P2 M Early HTTP failures prevent useful browser verification Inspected scalper.py:1015, 2470 Only a limited domain/error allowlist permits an inconclusive HTTP result to reach browser verification. Other blocking or transport errors discard candidates immediately. Classify transport/challenge errors separately from proven unavailable listings. Permit bounded browser verification where transport is inconclusive; keep final positive-evidence requirements strict. A blocked ordinary retailer can reach browser verification; sold, removed and identity-mismatched listings stay rejected; inconclusive checks never become availability.
P2 S Configuration validation is incomplete and optional during real runs Reproduced + inspected scalper.py:1649, 2419, 2593 Validation accepts targets missing fields needed by the prompt and an invalid timeout. Normal run does not invoke configuration validation; malformed configuration can fail mid-run. Validate required fields, unique IDs, numeric bounds, destinations, regex lists, timeout/result limits and coherent inherited settings before any side effect. Reject unknown requested target IDs. Missing name/search intent/price, invalid timeouts and unknown selected IDs fail promptly with actionable messages and no network, state or publication changes.
P2 S Diagnostic runs overwrite authoritative output Reproduced scalper.py:2421, 2561; README.md:26 Dry-run writes the selected public directory, whose default is production output. A single-target run rebuilds the snapshot from a subset and can influence later publication comparisons. Use temporary output by default for diagnostics; require an explicit diagnostic export; label partial scans and keep them separate from authoritative snapshots. Dry-run and filtered diagnostic leave live output and state byte-identical; exported diagnostic clearly states selected scope and dry-run status.
P2 M Lock skips and direct invocations are inadequately protected Observed skip; contention inferred; code inspected run_scalper.sh:15; scalper.py:312, 2419 A recent trigger exited without a scan log; lock contention is plausible but unproven. The wrapper silently skips a busy lock. Direct CLI runs bypass the lock and share a fixed state temporary name. Acquire state/run locking inside the application; use unique temporary state files and atomic replacement; log and export skipped-lock/startup outcomes without adding a new persistent scheduler. Two overlapping isolated runs preserve acknowledgements; a held lock records a skipped outcome; cleanup leaves no lock, state or publication collision.
P2 M End-to-end deadlines and failure isolation are incomplete Inspected scalper.py:555, 1079, 2354, 2463; otel_cron_runner.py:199 Per-target search has a deadline, but publication, lease release and the whole job do not. Candidate normalization and some browser/cleanup failures can escape the target-level handler. Use an overall job budget, bounded subprocess and browser calls, process-group cleanup where needed, per-candidate error isolation and guaranteed final status persistence. Hung Git/broker, malformed candidate and cleanup exception end within budget; later valid candidates/targets continue when appropriate; job failure is recorded.
P2 M Monitoring sees completion more clearly than discovery health Observed + inspected scalper.py:171, 2460; automation_health_digest.py:19, 337 Direct stage metrics are disabled in recorded cron runs, although wrapper/API monitoring remains. Raw/normalized/verified counts and coverage are absent; generic health can tolerate a 30-hour-old completion for an hourly job. Export coverage, stage counts, rejection/error categories, duration, last-success age and skips to the textfile collector. Feed failures and coverage gaps into the automation snapshot and Digest. Fresh empty scan stays healthy; blocked search, unattempted targets, missed schedules, delivery failure and publish failure appear distinctly. A zero streak alone is not proof of failure.
P2 M Partial target failures hide all good results downstream Inspected scalper.py:2448; digest_section_pages.py:399 A failed search is omitted and raises the aggregate exit code. The current section consumer then hides verified results from every successful target. Retain explicit per-target outcomes and consume successful fresh target results while prominently displaying incomplete coverage and failed target states. One successful target and one timeout produce a partial report with the good verified result, the failed target and a clear incomplete-coverage indicator.
P2 M Public payload and raw logs need an explicit privacy boundary Reproduced sanitizer gaps; no current leak found scalper.py:1954, 2097, 579 The sanitizer handles only three token formats. Synthetic personal identifiers, custom private destinations and query tokens survive. Raw subprocess error text and arbitrary model fields can enter public output. Limited current-artifact scans found no matching exposure. Publish an allowlisted summary schema; keep detailed traces private with bounded retention; sanitize URLs and personal fields; block publication on a failed privacy scan. Synthetic credentials, contact details, private endpoints and personal identifiers never reach the public build. Safe technical summaries remain useful.
P2 M Deduplication mixes identity and price and loses query identifiers Reproduced + inspected scalper.py:1798, 1859 Generic keys remove every query parameter, so distinct query-identified items at the same price collide. Price changes create a new identity; capped history can evict active items. Retain listing/variant identifiers and remove tracking keys only; separate identity, price history and delivery acknowledgements; define explicit re-alert and retention rules. Different query-identified items stay distinct; tracking variants collapse; price oscillation follows policy and does not cause accidental duplicate or suppressed alerts.
P2 S Publication freshness and status transitions are conflated Reproduced signature behavior scalper.py:2380, 2404 The signature includes targets but not status. Status-only changes can remain unpublished within the 12-hour heartbeat. Scan time, evidence time and public publication time are not consistently separated. Include status, target coverage and configuration revision in signatures; track per-target evidence time and last successful publication separately. Status-only failure publishes promptly; unchanged verified results refresh on schedule; consumers can distinguish current evidence from an older public snapshot.

Record executed queries, attempted/opened sources, truncation, token usage and timings. For ordinary consumer-product monitoring, evaluate bounded deterministic checks and use model assistance for discovery or ambiguous pages under an explicit budget. Representative benign-product fixtures show equivalent verification quality; budget exhaustion is reported as incomplete, and performed coverage is inspectable.
P3 M Legacy consumers and shared telemetry retain separate risks Legacy reproduced; shared-writer risk inspected scalper_digest.py:78; web_digest.py:628; automation_api_otel.py:205, 317 The callable legacy summary can label old cached offers active and prefer them over newer failed state, but normal current email integration replaces that fragment with the fresher section consumer. Shared telemetry uses thread locking/fixed temporary names across processes; actual loss was not shown. Retire or align the legacy consumer with the current result contract. Use interprocess-safe writes or a single aggregator for shared telemetry. Legacy and normal consumers agree on freshness/coverage; concurrent isolated telemetry writers retain every record without replacement collisions.
P3 L Tests and module boundaries need to match the real failure paths Observed passing tests; coverage inspected test_scalper_filters.py; test_ebay_validation.py; scalper.py 29 generic tests and 2 automation-health tests pass, despite the reproduced defects. Search, normalization, transport, delivery, state, rendering and Git are coupled in one large module. Add meaningful offline scenario tests for the findings; split components around a typed outcome/evidence contract; use an isolated ordinary-product smoke test for the real wrapper and consumers when verifying implementation. Acceptance checks above pass; a controlled integration run exercises the actual wrapper, state, rendering and consumer boundary without real notification or publication.
